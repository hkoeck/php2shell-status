## Key facts

- **Fixed upstream** in PHP **8.5.12, 8.4.27, 8.3.36, 8.2.35** (21 Oct 2026, embargo lift planned for 14:00 UTC). All earlier versions are affected (sources say back to PHP 5.4). PHP 8.1 and older get no release, but the PHP security team published **minimal source backports for 7.4, 8.0 and 8.1** (CERT-EU); distributions/LTS vendors ship their own backports.
- **Severity:** CVSS v4.0 **9.2** (PHP, both CVEs) · NVD CVSS 3.1 **9.8** · Red Hat / SUSE / Amazon CVSS 3.1 **8.1 (Important)** · Ubuntu priority **Critical**.
- **Most exposed SAPI:** Apache **mod_php** (RCE validated with default limits). For 109618, FPM is "susceptible" by source analysis, but no complete FPM exploit has been demonstrated; **for 109619, session-lifecycle RCE was validated against both mod_php and FPM** (PHP GHSAs). FrankenPHP: likely susceptible; LiteSpeed LSAPI: conditional.
- **Exploitation – treat as exploited:**
  - **Amazon Threat Intelligence** (AWS Security Blog, 21 Oct): first exploitation attempt in MadPot honeypots on **17 Oct 2026**, four days before disclosure; more attempts by multiple actors on 21 Oct 02:00–08:00 UTC; *"PHP2Shell is now seeing broad exploitation attempts in the wild."* (wording changed on 22/23 Oct; earlier: "is now being broadly exploited") Amazon recommends **investigating from 17 Oct onward**.
  - **Cloudflare** (blog, 21 Oct): "we observed attack traffic targeting our customers" while the bug was leaked; **watchTowr** (FAQ): "watchTowr has observed exploitation of both CVE-2026-109618 and CVE-2026-109619 in the wild" (Attacker Eye honeypots, 21 Oct).
  - **Public PoCs:** Rapid7 (upd. 22 Oct): "Multiple public proof-of-concept (PoC) exploits … are now available", each working only for a specific OS / PHP / web-server combination, "none appears to be broadly reliable"; "Rapid7 has not observed exploitation in the wild, though there are multiple reports of exploitation attempts". **Sansec** (upd. 22 Oct): "Mass exploitation of PHP2Shell is less likely than we expected on release day … The public exploits do not work against a default PHP installation." BSI v1.2 (22 Oct): PoC "öffentlich", "unbestätigte Berichte über existierende Exploits"; CCCS: "a Proof of Concept (PoC) is available, with no active exploitation being identified at this time". Imunify360: "an exploit tool also called PHP2Shell went public before PHP’s fix. By 11:00 UTC on 21 October, its requests had reached more than 3,600 servers in the Imunify defense network."
  - Official sources lag: **not in CISA KEV** (catalog 2026.10.21, re-checked 23 Oct 03:51–03:57 UTC); CISA alert (21 Oct): "CISA has not observed exploitation of these vulnerabilities as of the time of publication"; CISA SSVC (21 Oct 14:34 UTC) "Exploitation: none"; BSI (v1.2, 22 Oct): "noch keine bestätigten Ausnutzungen"; Canada CCCS: no active exploitation identified; Talos: none seen as of 21 Oct 14:00 UTC; Cisco PSIRT (v1.4, 22 Oct 23:00 GMT): "not aware of any malicious use"; QNAP: no reports of exploitation targeting QNAP products.
- **Mitigations are partial:** PHP names `memory_limit=-1` (109618) and `session.upload_progress.enabled=0` (one 109619 path) as incomplete config mitigations; watchTowr calls `.ini` mitigations "ineffective". Sophos additionally lists `fatal_error_backtraces=0` on PHP 8.5. **Only patching closes both bugs.** WAF rules (section 2) are defense-in-depth.
- **Look-back window:** Sophos states the PHP project received the first reports on 11 Aug 2026 and recommends reviewing exposed systems from **1 Aug 2026** (multipart POSTs to non-upload endpoints, `PHP_SESSION_UPLOAD_PROGRESS` in requests, memory-exhaustion errors and worker segfaults, admin logins).

## Checking whether you are patched

With backports, `php -v` keeps showing the old version. Check package versions or changelogs:

```sh
# Debian / Ubuntu (adjust php8.x)
zgrep CVE-2026-109618 /usr/share/doc/php8.4-fpm/changelog.Debian.gz
# RHEL / Alma / Rocky / Oracle / Fedora / SUSE / Amazon Linux
rpm -q --changelog php-fpm | grep CVE-2026-109618
# Remi
dnf list --updates --refresh --repo remi-modular
```

Restart PHP-FPM after updating; for mod_php do a full Apache restart. Rebuild container images; updating the host does not update PHP inside an image.
