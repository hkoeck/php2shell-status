## Key facts

- **Fixed upstream** in PHP **8.5.12, 8.4.27, 8.3.36, 8.2.35** (21 Oct 2026, embargo lift planned for 14:00 UTC). All earlier versions are affected (sources say back to PHP 5.4). PHP 8.1 and older get no release, but the PHP security team published **minimal source backports for 7.4, 8.0 and 8.1** (CERT-EU); distributions/LTS vendors ship their own backports.
- **New, related: CVE-2026-115560 (23 Oct, not fixed yet).** PHP [informational advisory](https://www.php.net/archive/2026.php) (23 Oct): "We suggest you set `session.upload_progress.enabled=0` until the next regular bugfix release, to fully protect from an unlikely RCE vector." It occurs only if an application sets `session.serialize_handler` to `php_binary` or `php_serialize` and then switches it to `php` at runtime with `ini_set()` before `session_start()`, with session upload progress still enabled; "Applications that never change the serialize handler at runtime can keep the feature enabled." It is handled "in the regular release cycle"; a full advisory follows with the next release. **The 21 Oct releases (8.5.12 etc.) do not fix it** (Cloudflare: "affects fully patched PHP releases, including 8.5.12"). So keep `session.upload_progress.enabled=0` after patching. No CVE record, no NVD entry, no Red Hat VEX and not in KEV (re-checked 27 Oct 06:28 UTC). Vendor statements: F5 [K000163878](https://my.f5.com/manage/s/article/K000163878) (pub. 23 Oct): BIG-IP 21.x/17.x and BIG-IQ 8.x still researched ("**"), mitigation file `/etc/php.ini.d/K000163878.ini` with `session.upload_progress.enabled = 0` (upd. 26 Oct: if the K000163821 mitigation was applied, "session.upload_progress.enabled = 0 is already configured"); Quest: "confirmed to not impact the KACE SMA and SDA systems"; Palo Alto (FAQ, 25 Oct): "Current analysis shows no impact of CVE-2026-115560 on PAN-OS (NGFW and Panorama) … A review of impact to other products is underway"; LibreNMS Docker [26.10.2-r2](https://github.com/librenms/docker/releases/tag/26.10.2-r2) (25 Oct 13:52 UTC) sets `session.upload_progress.enabled=0` "as a precaution against CVE-2026-115560"; Red Hat RHSB-2026-013 (upd. 23 Oct 13:15) now covers it. Cloudflare: existing rule "#6" covers it if the default `session.upload_progress.name` is used
- **Known regression in the 21 Oct releases** (not in the security fixes): [php-src #24488](https://github.com/php/php-src/issues/24488) (opened 21 Oct, label "Status: Verified"): "8.4.27 / 8.5.12 regression: GC double-frees the SimpleXMLElement properties table (`zend_mm_heap corrupted`), introduced by the GH-24050 fix". It needs a SimpleXML object whose properties table was materialized (`get_object_vars()`, an `(array)` cast or `json_encode()`) and that the GC collects in a cycle; "It passes on 8.4.26." Fixed in commit [f963484](https://github.com/php/php-src/commit/f9634847258a8c3ed6c12bb79104eba60bb631ea) (22 Oct), which is on the PHP-8.4, PHP-8.5 and master branches; no release contains it yet (no `php-8.4.28` or `php-8.5.13` tag, 27 Oct 06:28–06:31 UTC). Do not roll back to unpatched versions; test SimpleXML-heavy applications after updating.

## Checking whether you are patched

With backports, `php -v` keeps showing the old version. Check package versions or changelogs:

```sh
# Debian / Ubuntu (adjust php8.x)
zgrep CVE-2026-109618 /usr/share/doc/php8.4-fpm/changelog.Debian.gz
# RHEL / Alma / Rocky / Oracle / SUSE / Amazon Linux
rpm -q --changelog php-fpm | grep CVE-2026-109618
# Remi
dnf list --updates --refresh --repo remi-modular
```

Restart PHP-FPM after updating; for mod_php do a full Apache restart. Rebuild container images; updating the host does not update PHP inside an image.

## Fork it and keep it current with an AI

1. Fork: click **Fork** on GitHub, or `gh repo fork hkoeck/php2shell-status --clone`.
2. Open the fork in an AI coding assistant with shell and web access (e.g. Claude Code) and give it the prompt from [UPDATE_PROMPT.md](UPDATE_PROMPT.md). Fill in the placeholders: the products to add, or "update everything".
